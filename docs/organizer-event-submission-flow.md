# Organizer event submission flow

1. An approved organizer opens Create Event. The frontend checks `GET /api/organizer/terms-acceptance`. If the account has not accepted the terms, it shows them before the form. Checking the agreement calls `POST /api/organizer/terms-acceptance` and persists the timestamp on the user account; later events and drafts skip this gate, including on another device. An API error never counts as acceptance. Existing organizers with an `event.terms_accepted` audit entry are backfilled by migration `20261016000000_organizer_terms_acceptance`. A previously confirmed account phone is not required merely to open the editor or save a draft.
2. The organizer completes the form and may save drafts without an OTP. Drafts stay owner-scoped and are not public.
3. Submit validates the complete form, then asks the organizer for a Lao mobile number. If their Supabase Auth identity already has a confirmed phone, the entered number must match it. Otherwise this event-specific OTP verifies possession of the entered number. `POST /api/organizer/event-submission-otp` sends a new six-digit Wenova SMS. The code expires after five minutes. Requests have a 60-second per-account cooldown and an IP rate limit; attempts are capped at five. If Wenova's response is uncertain, the UI retains the challenge so a code that arrives can still be used without automatically sending another paid SMS.
4. The final event create/update request includes `submissionOtp: { challengeId, code }`; already accepted terms do not need to be accepted again. The backend checks the code and consumes it in the same database transaction as the event status change. A replay or missing code cannot submit another event. Organizers submit for admin review; only admins publish.

This challenge is separate from the login and initial organizer-enrollment OTP. The code is never stored in plaintext or logged. Migrations `20261015010000_event_submission_otp` and `20261016000000_organizer_terms_acceptance` must be applied before deploying the new backend. It uses the existing backend-only Wenova configuration and `SUPABASE_SEND_SMS_HOOK_SECRET`; no new frontend secret is needed.

## Event form persistence and registration

Draft and submission requests use the same form payload. All four steps, including guest-information requirements, custom questions, sale windows, booking capacities and coupon settings, are saved through `/api/events`. Unlimited per-order tickets are stored as SQL NULL, not zero. Calendar dates are normalized to ISO dates; coupon and sale-time boundaries use Asia/Vientiane (UTC+07:00).

Apply migration `20261016010000_event_form_coupon_limits` before starting the updated backend (`npm run db:migrate`). It adds nullable coupon per-user and maximum-discount limits without changing existing coupons. Generate the Prisma client during the build. Deploy the backend with the migration before the frontend.

Public event responses expose registration questions, sale windows and booking capacities as separate fields. Bank account information and online meeting secrets remain in owner/admin-only `privateDetails`. Ticket creation validates required answers, sale windows, session capacity and coupon validity/usage on the server. Event row locking protects session and coupon limits during concurrent purchases. Pending, unexpired orders reserve coupon usage; cancelled/expired reservations do not count.

Coupons apply to one ticket type per checkout in the current frontend. Discount amounts are calculated by the backend; a fully discounted order can be confirmed without payment. Orders with a positive balance remain pending and the frontend keeps paid checkout disabled until a real payment provider is configured. Saving an event or coupon is not evidence that paid checkout is enabled.

Verification: `npm test` runs migrations and API tests against an isolated temporary PostgreSQL cluster. `tests/event-form.test.ts` exercises the real frontend payload mapper through event creation/read/update, public question visibility, private-field isolation, coupon limits, sale windows, and booking-capacity races.
